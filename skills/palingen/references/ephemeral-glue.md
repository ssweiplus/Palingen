# Agent-Generated Ephemeral Glue

Ephemeral Glue is temporary, local, low-risk deterministic code generated by the Agent to bridge a small representation or interface mismatch without prematurely creating a permanent component.

> **Generate glue only when composition is cheaper than construction.**

## Good candidates

- one-off field reshaping;
- temporary file-format conversion;
- extracting selected JSON fields;
- joining artifacts;
- simple CLI-output preprocessing;
- temporary renaming or path conversion.

Prefer existing Tools or deterministic utilities before generating new glue.

## Poor candidates

Do not use Ephemeral Glue as the owner of:

- authorization or permission decisions;
- production-destructive actions;
- durable state migration;
- security boundaries;
- high-risk business rules;
- semantic judgments that belong to the Agent.

A useful boundary is:

```text
Representation adaptation -> Ephemeral Glue
Semantic interpretation   -> Agent
```

## Traceability

> **Ephemeral does not mean invisible.**

When generated glue materially contributes to a result, preserve enough execution truth to reconstruct what happened:

- generated code or equivalent reproducible content;
- input artifact references;
- output artifact references;
- execution parameters;
- stdout / stderr;
- exit status;
- timestamp.

The exact persistence mechanism may remain lightweight. Do not require every five-line script to become a committed source file.

## Execution boundary

Generated code should run through a constrained execution boundary appropriate to its risk. Prefer scoped filesystem access, limited permissions, and explicit artifact inputs/outputs rather than unrestricted ambient authority.

## Promotion signals

Consider promoting ephemeral glue when real usage shows:

- repeated recurrence;
- stable rules;
- clear inputs and outputs;
- rising failure cost;
- reuse across tasks or Agents;
- need for tests, permissions, performance, or maintenance.

Possible evolution:

```text
Ephemeral Glue
    -> reusable Lubricant
    -> Tool, when it becomes an independent capability
```

Do not promote merely because a script appeared a fixed number of times.

> **Promote only when repeated friction becomes cheaper to encode than to regenerate.**

## Relationship to incremental Agentification

Agentification need not perfect every boundary in one pass. Prefer coarse safe reuse first and refine from observed friction. When useful, keep a lightweight `.agentification.md` containing current boundaries, known compromises/assumptions, and revisit triggers. Do not turn this into a heavy process requirement.
